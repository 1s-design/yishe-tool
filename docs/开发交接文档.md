## 1. 项目概览

三个仓库协同工作，**AI 生产能力全部跑在浏览器端（1s），服务端只做转发与资源存取**。

| 仓库 | 路径 | 技术栈 | 职责 |
|---|---|---|---|
| **1s** | `/Users/jackie/workspace/1s` | Vue3 + TS + Vite | 设计工具前端；AI agent、画布渲染、批量生产引擎都在这里 |
| **design-server** | `/Users/jackie/workspace/design-server` | NestJS + MySQL + Redis | 业务后端；MCP 工具暴露、资源库、灵感库、字体库、贴纸库 |
| **yishe-admin** | `/Users/jackie/workspace/yishe-admin` | Vue3 + element-plus + vxe-grid | 管理后台；资源审核与维护 |

远端：
- 1s → `git@github.com:1s-design/yishe-tool.git`
- design-server → `https://github.com/1s-design/yishe-server.git`

### 核心链路

```
外部 Agent / 编排脚本
      │  MCP (HTTP)
      ▼
design-server :1520  /api/ai-assistant/tools/execute
      │  Socket.IO 下发命令
      ▼
1s 设计端（浏览器）:1522
      ├─ AI agent（simple.ts）→ 直连大模型
      ├─ 画布渲染（HTML/CSS → PNG）
      └─ 保存到 COS + 回写数据库
```

**关键理解**：设计端必须开着浏览器页面并连上 WebSocket，MCP 命令才有落点。没有在线设计端时，所有 `batch_start` 等命令都会失败。

### 3.2 渲染与画布

- 设计稿是 **HTML/CSS**，渲染成 PNG 走 `services/websocketClient.ts` 的 `renderNodeToCanvas`
- **不依赖 `requestAnimationFrame`**（后台标签页 rAF 不触发，会导致渲染永不结束）
- 保存前会跑 `canvas-audit.ts`，不通过则自动修复或让模型重做

### 3.4 资源引用系统（重点）

一份引用集合 = UI 托盘 state = MCP `resources` 参数，两条路产出完全一致。

```ts
interface DesignResourceRef {
  type: "inspiration" | "font" | "image" | "sticker" | "sentence" | "document" | "tip" | "prompt";
  id: string;
  label?: string;
  payload?: Record<string, any>;   // 提供后免去按 id 取数
  asReference?: boolean;           // 仅 image/sticker：是否作为视觉参考喂视觉模型
}
```

编译产物（`buildResourceContext()`）：

1. **promptContext** — 思路上下文（主题/氛围/约束/可用文案）
2. **htmlBindings** — 真正进设计的绑定：字体 → `{{font.键.family}}`，图片 → `{{image.键.url}}`
3. **resourceHints** — 检索方向
4. **referenceImage** — 视觉参考图（第一个 `asReference` 的图）

**资源冲突优先级**（写死在 `resource-refs.ts`）：

```
1) 灵感        → 决定主题与配色
2) 提示词/技巧 → 只作约束与形态参考
3) 文案        → 提供可选文案
4) 字体/图片/贴纸 → 必须实际使用（字体进 font-family，图片进 {{image.xxx.url}}）
```

## 5. 关键设计决策（含踩坑记录）

这些是排查时最花时间的坑，改代码前务必先读。

| # | 现象 | 真因 | 解法 |
|---|---|---|---|
| 1 | 保存失败「画布渲染超时」 | 中文字体全量 base64 嵌入，SVG data URL 数十 MB | **字形子集化**（`font-subset.ts`） |
| 2 | 后台标签页渲染永不结束 | `html-to-image` 的 `createImage` 依赖 `requestAnimationFrame`，隐藏标签不触发 | 自实现 `loadImageWithoutRaf` |
| 3 | 文字显示不全 | `overflow-validator` 的自动修复是**裁切**（ellipsis / nowrap / overflow:hidden） | 改为换行 + 限宽 |
| 4 | 画布残留旧内容 | `add-child` 的「新 HTML < 上一张 65% 就拒绝替换」误杀更简洁的合法设计 | 改为结构判断 |
| 5 | 误报「找不到文案」 | 注入的 `<style>` 里 CSS 选择器文本被 `textContent` 读到 | 文案检查排除 `<style>/<script>` |
| 6 | 误报「主文案过高」 | 测的是居中容器整体框（含副文案） | 只量字号最大的那一行 |
| 7 | 自动居中无效 | `left:50%` 相对最近定位祖先 | 按测量偏移量用 `transform: translate(dx,dy)` |
| 8 | 自动修复缩不动 | 逐次 ×0.85 缩到次数用尽 | 一次算准比例 |
| 9 | 重做丢资源 | `_runBatchItem` 每次清空对话，审查重做的 prompt 没带资源 | 重做/修订 prompt 也带资源与参考图 |
| 10 | `resetBatch()` 撤销停止 | 会把 `controlSignal` 重置为 running | 停止用 `stop`，不要跟 `reset` |
| 11 | `batch_start` 误判失败 | 立即返回 `phase=progress`（不带 batch 字段） | 必须轮询 `batch_get_state` |
| 12 | 灵感分页只取 100 | 后端 pageSize 上限 | `inspAllPages()` 翻页取全量 |
| 13 | Vite 代理路径 | `/api` 会 strip 前缀，前端 `baseURL=/api` + `/api/xxx` = `/api/api/xxx` | 剥一层后正好对，不要"修" |
| 14 | **复刻产出完全不一样** | 见第 6 节（视觉链路三处断点） | v0.0.82 已修 |
| 15 | 下拉菜单点了没反应 | radix-vue `as-child` 与卡片 `@click` 的处理器合并冲突；且 portal 层级被资源浮层（z-9999）压住 | 弃用 radix 下拉，改手写 Teleport 菜单（z-10002） |
| 16 | loading 遮罩白底 | 硬编码 `rgba(255,255,255,.7)`，暗色规则用的 `.dark` 类匹配不上（设计端实际是 `body.designiy-dark`） | 改用主题变量 `color-mix` |
| 17 | 催促消息撑爆上下文 | agent 不调 `addHtml` 时每轮追加一条催促，堆叠 376 条后模型停调工具 | 去重，只保留一条 |
| 18 | 视觉任务超时 | 读图 + 设计更耗时，15 分钟不够 | 带 `referenceImage` 时超时上浮 50% |

## 6. 视觉参考链路（v0.0.82 修复详情）

**问题**：用带图灵感复刻时产出与参考图完全无关。

**真因是三处断点叠加**，不是视觉模型不准：

1. **灵感路径从不传图** — `generateInspirationBriefs` 用**纯文本** LLM 编译 brief，图片 URL 只作为 JSON 字符串塞给它（模型看不见），且 brief 从未设 `referenceImage` 字段（全库只有 `generateImageBriefs` 设了）
2. **调用口丢参** — 三处 `_runBatchItem(buildDesignPrompt(...))` 都没传第二个参数 `{ referenceImage }`，即使 brief 有图也会被丢掉（**图片复刻路径同样断**）
3. **图文冲突无裁决** — brief 里 LLM 发明的主题（如「桌面漫游」暗蓝风）压过了参考图，agent 明确说「本次按提示词指定内容与配色执行」

**修复内容**：

- 三处 `_runBatchItem` 补传 `referenceImage`
- 灵感 brief（LLM 路径 + 本地兜底）带图时挂首图到 `brief.referenceImage`
- 带图灵感的 brief **禁止发明主题/文案/配色**，全权交给看图环节
- 设计 prompt 增加**冲突裁决**：brief 与参考图冲突一律以图为准
- 视觉降级由静默 console 改为**显式提示**（含原因）
- 催促消息去重
- 带参考图的设计超时 ×1.5

**验证结果**（灵感「鼠标垫印花」= 红底金字锦鲤桌垫）：主文案「锦鲤附体」逐字保留 ✅、金色调 ✅、锦鲤元素 ✅；仅底色由深酒红漂移为蓝橙 ⚠️（**未解决**，见第 8 节）。

## 8. 已知问题与待办

### 高优先级

1. **带图灵感底色提取偏差** — 参考图是电商截图（含米色背景、键盘鼠标等非印花区域），取色被干扰。建议加「只取印花区域主色」的裁决，或先裁剪再喂视觉模型。
2. **`list_resources` 的 keyword 未生效** — 传不同 `keyword` 返回同一批字体（始终是 LXGWBrightCode 系列），说明关键字没进检索条件。
3. **视觉任务耗时长** — 单张 5–15 分钟，长尾会触发超时。2000 张产能目标下需要并行多设计端（一机一尺寸）。

### 中优先级

4. **brief 编译仍是纯文本 LLM** — 带图灵感的 brief 现在靠"禁止发明"规避，但更彻底的做法是让 brief 编译也用视觉模型（或直接复用 `generateImageBriefs` 的模板）。
5. **背景丰满度方差** — 部分设计只有渐变，缺少具象元素。建议按尺寸加「版面规约」（方形/横幅分别规定最少具象元素数）。
6. **资源冲突仍偶有波动** — 优先级规则已写死，但 agent 执行有随机性，建议在审查阶段加「绑定资源是否被使用」的校验。

### 低优先级

7. `graph.ts` + `nodes/`（LangGraph 版）未接入，可考虑清理或补齐。
8. `customSticker` / `designInspiration` 不是 `list_resources` 支持的类型（目前用 `sticker`/`image` 代替）。
